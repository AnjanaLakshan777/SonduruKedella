# Database Guidelines

## Database
PostgreSQL is the system of record for business and financial data. Local development uses Docker Compose with a named persistent volume.

## Schema Management
Use Flyway versioned SQL migrations. Do not use Hibernate schema auto-update as the production schema management strategy. Do not edit an already-applied migration in shared or persistent environments; create a new migration instead.

## Monetary Data
Use Java BigDecimal and suitable PostgreSQL NUMERIC types. Define scale and rounding policies deliberately. Never use floating-point types for money calculations.

## Core Business Areas
- Clients and contact details.
- Projects, contract values, deadlines, and payment schedules.
- Revenue and client receipts.
- Project expenses and company-level expenses.
- Commission recipients, confirmed commission terms, and payments.
- Suppliers, invoices, and partial payments.
- Materials, stock movements, and project issues.
- Employees, attendance, overtime, advances, and weekly payroll.
- Machinery rental expenses with machine and usage period.
- Document metadata and audit history.

## Financial Integrity Rules
1. Revenue records and receipts are separate concepts.
2. A client receipt must not be counted as new revenue repeatedly.
3. Supplier purchases and supplier payments are separate records.
4. Commission is calculated from the agreed contract value using the confirmed percentage and recorded calculation basis.
5. Multiple commission recipients must be supported without silently exceeding the configured allocation policy.
6. Delay deductions must not overwrite the original contract value.
7. Written-off receivables are not payments received.
8. Payroll advances must not be counted twice when deducted from weekly payroll.
9. Inventory acquisition and project stock issue must not double-count expense.
10. Project expenses must remain distinguishable from company-level expenses.

## Data Integrity
Use foreign keys, NOT NULL constraints, unique constraints, CHECK constraints, and indexes where appropriate. Use transactions for multi-record financial operations. Use optimistic locking or other suitable concurrency protection where simultaneous updates could cause incorrect balances.

## Deletion and Audit
Avoid hard deletion of finalized financial records. Use controlled correction, reversal, cancellation, or write-off workflows with a reason and audit history where appropriate.

## Development Safety
Never run destructive database resets against a database containing data that must be preserved. Back up data before risky schema operations. Verify migrations against the actual PostgreSQL version and schema.

# Proposed Schema (v2, owner decisions applied 2026-10-24)

Status: implemented by `V1__initial_schema.sql`. JPA entities exist for the Settings tables (`company_profile`, `commission_policy`, `wage_settings`, `expense_categories`, `units`, `payment_methods`), `clients`, `projects`, `installments`, `delay_deduction_terms`, `activity_log`, `project_agreements`, `client_payments`, `receivable_write_offs`, `expenses`, `expense_payments`, `suppliers`, `materials`, `stock_movements`, `stock_cost_layers` and `stock_cost_allocations` (the last two added by V4), and the payroll tables (`employees`, `attendance`, `overtime_entries`, `salary_advances`, `payroll_adjustments`, `payroll_lines`, `payroll_line_costs`, `advance_recoveries`, `payroll_corrections`, `payroll_payments`), the commission tables (`commission_arrangements`, `commission_payments`) and, from V5, `app_users` and `security_events`. The other tables have no entities yet.

Scope: the schema supports what the existing frontend does (`frontend/src/data/types.ts`, `store/store.ts`, the forms and `lib/finance.ts`), the inventory return action the owner has approved, and the business rules the owner has agreed. Anything else the UI does not offer is left out. The frontend changes these decisions need are listed under [Frontend alignment](#frontend-alignment).

## Conventions

- Tables are plural `snake_case`. Columns are `snake_case`. Fixed enumerations are `VARCHAR` with a `CHECK` constraint, mapped to Java enums with `EnumType.STRING`. Lists the owner can edit in Settings are lookup tables.
- Primary keys: `id BIGINT GENERATED BY DEFAULT AS IDENTITY`.
- Types:
  - Money: `NUMERIC(15,2)`, rounded `HALF_UP` to 2 decimals.
  - Percentages: `NUMERIC(7,4)`, where `20.0000` means 20%.
  - Quantities: `NUMERIC(14,3)`.
  - Unit costs: `NUMERIC(15,4)`.
  - Hours: `NUMERIC(4,2)`.
  - Dates: `DATE`.
  - Instants: `TIMESTAMPTZ`.
- Every table has `created_at`, `created_by` and `updated_at`. Tables whose rows can change also have `version BIGINT` for optimistic locking.
  - `created_by` references `app_users` and is nullable. Since 2026-10-25 the application fills it with the signed-in user (null for work done without a signed-in user, such as startup tasks).
  - Append-only and frozen tables (`stock_movements`, `stock_cost_allocations`, `payroll_lines`, `payroll_line_costs`, `advance_recoveries`, `activity_log`) have no `updated_at` or `version`.
- Single-row settings tables use `id SMALLINT = 1`.
- Some child tables carry a copy of a parent value, such as `project_type`, `allocation` or `expense_group`. That copy lets a composite foreign key enforce a cross-table rule in the database. The service sets the copy, and the foreign key guarantees it matches the parent.
- **Payments** (client, other income, expense, supplier, commission, payroll) and **salary advances** follow the same rules:
  - Columns: `payment_date`, `amount > 0`, `payment_method_id`, `reference`, `notes`, `request_id UUID UNIQUE`.
  - Each one settles exactly one obligation.
  - The service locks the parent row and rejects any amount above the remaining balance. This matches the UI's "More than the remaining…" check.
  - Payments are never deleted. A correction voids the row (`voided_at`, `void_reason`), and voided rows are left out of every balance.
- Index every foreign key, plus the date columns that reports filter on.
- Balances are calculated, never stored. That covers outstanding, overdue, advance balances and payroll figures. There are two deliberate exceptions:
  - the running stock balance on each stock movement, and the FIFO cost layers' remaining quantity and value, which are kept in step with it in the same transaction
  - the frozen payroll snapshot

  Both are described below.

## Settings and shared tables

- **company_profile**: a single row with `name`, `tagline`, `address`, `phone`, `email`, `registration_no`, `owner_name`, `financial_year_start_month` (default 4, for 1 April) and `supplier_credit_days` (default 14).
- **commission_policy**: a single row.
  - `design_commission_pool_pct` (default 20). The company share is shown as 100 minus the pool.
  - `construction_warning_pct` (nullable).
  - Both values only trigger warnings.
- **wage_settings**: a single row with `default_daily_wage`, `hours_per_day` (default 8), `overtime_multiplier` (default 1.5), `payday` (`FRIDAY` | `SATURDAY`). The payroll week starts on Monday.
- **expense_categories**:
  - Columns: `expense_group` (`DESIGN` | `CONSTRUCTION` | `CONSULTATION` | `COMPANY`), `name`, `locked`, `system_generated`, `active`, `sort_order`.
  - Unique (`expense_group`, `name`).
  - `Materials`, `Labour` and `Commission` are `locked`. `Labour` and `Commission` are also `system_generated`, so a manual expense cannot use them.
  - A category removed in Settings is set `active = false`, so expenses that already use it keep their history.
  - The seed data is the frontend's default category list.
- **Revenue categories** are fixed and have no table: Design, Construction, Consultation and Other Income. The category comes from `projects.project_type`, and `other_income` is always Other Income. Settings shows the list read-only.
- **units** and **payment_methods**: editable lists (`name` unique, `active`). Seed payment methods: Cash, Bank Transfer, Cheque, Online Payment.
- **app_users**: `username` (unique, and unique ignoring case via `uq_app_users_username_lower`), `display_name`, `password_hash` (BCrypt, `{bcrypt}` prefix; never plain text), `enabled`.
  - V5 added `role` (`SUPER_ADMIN` | `ADMIN`, no default) and `auth_version` (bumped when access changes, which ends existing sessions).
  - Users are never deleted, only deactivated, because every `created_by` and `security_events` row points here.
  - The partial index `ix_app_users_active_super_admins` serves the "at least one active Super Admin" check.
- **security_events** (V5): the security audit trail. Columns:
  - `event_type`, checked against the `SecurityEventType` values;
  - `actor_user_id` and `target_user_id`, nullable FKs to `app_users`;
  - `username`, as typed at sign-in;
  - `remote_address`, `details`, `occurred_at`.

  Append-only (`trg_security_events_immutable`, using V1's `sk_reject_change`). It never holds a password, hash or session id. Indexed by time, actor and target.
- **activity_log**: `project_id` (nullable), `activity_date`, `kind` (`PAYMENT` | `EXPENSE` | `DOCUMENT` | `STATUS` | `COMMISSION` | `NOTE` | `WRITEOFF` | `DEDUCTION`), `message`. It feeds the project activity feed.

## Clients and projects

- **clients**: `name`, `client_type` (`INDIVIDUAL` | `BUSINESS`), `phone`, `email`, `address`, `city`, `notes`.
- **projects**:
  - Columns:
    - `code` (unique), `name`, `client_id`
    - `project_type` (`DESIGN` | `CONSTRUCTION` | `CONSULTATION`)
    - `location`, `description`
    - `contract_value`, `start_date`, `expected_completion`, `actual_completion`
    - `status` (`PLANNING` | `IN_PROGRESS` | `ON_HOLD` | `COMPLETED` | `CANCELLED`)
    - `notes`, `version`
  - Checks:
    - `contract_value > 0`, except for consultation projects, where the agreed fee is optional and may be 0.
  - Rules:
    - The contract value and the project type cannot be changed after the project is created. The UI only lets you change the status.
    - Setting the status to `COMPLETED` fills in `actual_completion` with the Asia/Colombo date if it is empty. Reopening keeps it, and completing again does not overwrite it.
    - `code` is assigned by the server as `PRJ-YYYY-NNN`, numbered per start-date year (owner decision, 2026-10-24). A per-year advisory lock prevents concurrent creates from picking the same number, and `uq_projects_code` is the backstop.
  - A second unique key, (`id`, `project_type`), lets child tables restrict a feature to certain project types through composite foreign keys.
- **project_agreements**: at most one current agreement PDF per project.
  - Columns: `project_id`, `original_filename`, `content_type` (check `application/pdf`), `size_bytes`, `sha256`, `storage_key` (unique), `uploaded_at`, `removed_at`.
  - Unique `project_id` where `removed_at IS NULL`.
  - Replacement (implemented 2026-10-24, no migration needed): the service sets `removed_at` on the current row and inserts the new one in a single transaction. The superseded row and its PDF are kept, because the row still points at the file; nothing is hard-deleted. There is no API that lists superseded agreements.
  - `storage_key` is a server-generated `<uuid>.pdf` inside the private storage directory. It is never returned to clients. `sha256` and `size_bytes` are computed from the bytes actually received, not taken from the client.

## Revenue and receivables

- **installments**:
  - Columns:
    - `project_id`, `description`, `due_date`, `amount > 0`
    - `kind` (`SCHEDULED` | `VARIATION`)
    - `billed_on` (nullable; null means not yet billed)
    - `version`
  - Schedule rules (enforced by the service):
    - Scheduled installments add up to `contract_value`. After variations, the whole schedule adds up to `contract_value + Σ variations`.
    - An installment that has been billed or has payments cannot be edited or removed. This matches the locked rows in the schedule editor.
  - Variations:
    - "Additional work billed" adds a `VARIATION` installment that is billed immediately.
    - The contract value does not change.
- **client_payments**: `installment_id` plus the common payment columns. A payment is allowed only when `billed_on` is set and a balance remains.
  - Implemented (2026-10-24). The installment row is locked (`SELECT … FOR UPDATE`) before the balance is read, so concurrent receipts cannot overpay.
  - `request_id` is the client-sent idempotency key. Resending the same request returns the original receipt; reusing the id for a different payment is a 409.
  - Corrections only void (`voided_at`, `void_reason`), which is all the V1 trigger allows. Voided receipts are kept and listed, but never counted.
- **receivable_write_offs**: `installment_id`, `write_off_date`, `amount > 0`, `reason` (not null). Allowed only on billed installments that still have a balance. A write-off is never a payment.
  - Implemented (2026-10-24): create only, under the same installment lock as receipts. The reason must be at least 10 characters after trimming (the UI rule).
  - Reversal (V7, 2026-10-26): `voided_at`, `void_reason` and `version`, guarded by `trg_receivable_write_offs_guard` (V1 `sk_guard_payment_change`). A reversed write-off is kept and listed but never counted. Reversing takes the installment lock and only raises what is owed.
- **delay_deduction_terms**: one row per construction project. It holds both the agreed terms and the deduction that was applied.
  - Columns for the terms:
    - `project_id` (unique), `project_type` (check `CONSTRUCTION`, composite FK)
    - `enabled`, `contract_deadline`
    - `rule` (`PER_DAY` | `PERCENT_PER_WEEK` | `FIXED_AMOUNT`), `rate_per_day`, `percent_per_week`, `fixed_amount`
    - `grace_days ≥ 0`, `max_deduction`
  - Columns for the applied deduction: `actual_completion`, `applied_amount`, `applied_on`, `applied_installment_id`, `notes`, `version`.
  - Checks:
    - The value column that matches `rule` is required.
    - The applied columns are either all set or all null.
  - Rules:
    - The applied amount cannot exceed the target installment's amount.
    - Clearing the applied columns reverses the deduction, as the UI's reverse action does. The activity log records both events.
    - Implemented (2026-10-24): applying and reversing lock the terms row; applying locks the target installment first, in the same order receipts use. The calculation and limits are under [Calculations](#calculations).
- **other_income**: `income_date`, `description`, `payer`, `amount > 0`, `due_date`, `reference`, `notes`. It is not linked to a project.
- **other_income_receipts**: `other_income_id` plus the common payment columns.

## Commission

- **commission_arrangements**:
  - Columns:
    - `project_id`, `project_type` (check `IN ('DESIGN','CONSTRUCTION')`, composite FK, so consultation projects cannot have commission)
    - `recipient_name`, `role`
    - `rate_pct` (`> 0 AND < 100`)
    - `status` (`PENDING` | `CONFIRMED`), `confirmed_on`, `commission_amount`, `policy_exception`
    - `version`
  - Amount = `round(contract_value × rate_pct / 100)`.
  - On confirmation, the amount is stored in `commission_amount`, which is required for `CONFIRMED` rows. This preserves confirmed commission history.
  - If the total of a project's rates goes above the design pool or the construction warning level, the service returns a warning and changes nothing. The owner may still confirm, and `policy_exception = true` records that.
  - V6 added `VOIDED` to the status, with `voided_at` and `void_reason` (both set together, only on a once-confirmed row).
  - The trigger `trg_commission_arrangements_guard` refuses any change to a `CONFIRMED` row except voiding it, any change to a `VOIDED` row, and deleting anything but a `PENDING` draft.
  - The partial unique index `uq_commission_arrangements_recipient_role` allows one live (non-voided) arrangement per project, recipient and role, ignoring case.
- **commission_payments**: `arrangement_id` plus the common payment columns.

**Commission rules as implemented (2026-10-25)**
- Recipient: a name on the arrangement (stored trimmed, inner spaces collapsed), as in the UI. There is no recipients table: it was removed from the schema by owner decision (see "Frontend alignment"). So there is no recipient activation or deactivation; the "by recipient" view groups confirmed arrangements by name, ignoring case.
- Base and amount:
  - The base is the project's agreed `contract_value`. It is never the billed or collected amount (financial integrity rule 4, the Commissions tab).
  - `amount = round(contract_value × rate_pct / 100, 2, HALF_UP)`, worked out per arrangement.
  - On confirmation the amount is stored in `commission_amount`, with `confirmed_on` (Colombo date) and `policy_exception`.
  - The contract value can't change after a project is created, so the stored amount stays reproducible. Later policy changes never touch it.
- Design split (the approved 80/20):
  - `commission_policy.design_commission_pool_pct` is the commission share (seeded 20); the company share is 100 − pool.
  - The pool amount is `round(contract_value × pool / 100, 2, HALF_UP)`, and the company share amount is `contract_value − pool amount`. So the two add up to the contract value to the cent, and the residual cent always goes to the company.
  - The pool is shared by the project's recipients. If their rates add up to more, it is a warning, not a cap.
- Construction:
  - Each arrangement's rate is agreed per recipient. No rate is assumed, and the design pool never applies.
  - The only check is the optional `commission_policy.construction_warning_pct`, a warning like the design pool.
- Lifecycle:
  - `PENDING` (a draft: editable and removable; not a cost).
  - `CONFIRMED`: the cost is recognised and the row is frozen.
  - Then `CONFIRMED` with payments shows as partly paid or paid, or the row becomes `VOIDED`. A void needs a reason, and all its payments must be voided first.
  - A wrong confirmed row is corrected by voiding it and adding the right one; both stay in the history and the activity log.
- Payments:
  - only on `CONFIRMED` rows, and never more than `commission_amount − Σ active payments`;
  - no future payment date;
  - an active payment method;
  - a unique `request_id`: a resent request returns the first payment, and the same id with different details is a 409;
  - voidable with a reason (V1 trigger).

  The arrangement row is locked for every payment and void.

## Expenses

- **expenses**: manual expenses.
  - Columns:
    - Core: `expense_date`, `scope` (`PROJECT` | `COMPANY`), `project_id`, `category_id`, `description`, `payee`, `supplier_id` (nullable), `amount > 0`, `due_date`, `invoice_no`, `notes`.
    - Materials: `quantity`, `unit_id`, `unit_price`.
    - Machinery rental: `machine_type`, `usage_from`, `usage_to`.
    - Electricity: `billing_period`.
    - Attachment: `attachment_storage_key`, `attachment_filename`, `attachment_size`.
    - `version`.
  - Checks:
    - `project_id` is set exactly when `scope = 'PROJECT'`.
    - `usage_to ≥ usage_from`.
    - For materials, `amount = round(quantity × unit_price, 2)`.
  - Rules, enforced in the database through the copied columns `expense_group`, `project_type` and `category_system_generated`:
    - The category's group must match the expense: the project's type for project expenses, `COMPANY` for company expenses.
    - `system_generated` categories are rejected.
- **expense_payments**: `expense_id` plus the common payment columns. The expense form's "paid in full / part / unpaid" choice creates zero or one payment in the same transaction.

Machinery rental is a manual expense in the `Machinery Rental` category, recording the provider, machine type, usage period and project, with payments recorded against the expense. There is no separate rental module.

**Implemented (2026-10-24, no migration needed)**
- Only manual expenses are stored here. Labour (payroll), commission, supplier invoices and stock issues reach project costs through their own modules. The service rejects `system_generated` categories (Labour, Commission) with a clear message, and the V1 check refuses them as well. Materials is not system-generated, so a purchase made outside the inventory workflow is a valid manual expense.
- Scope:
  - `PROJECT` needs an existing project. Its type sets `expense_group` and `project_type`.
  - `COMPANY` must have no project. Company expenses never appear in a project's list or costs.
  - New expenses cannot be added to a `CANCELLED` project; the UI doesn't offer cancelled projects either.
- Category: it must exist, be active, belong to the expense's group and not be system-generated. On an edit, a category, unit or cancelled project the expense already had is still accepted, so historical expenses stay editable.
- Materials line: `quantity`, `unit_id` and `unit_price` come together. The amount is worked out as `round(quantity × unit_price, 2)` (`HALF_UP`, as the V1 check does). A client-sent amount must match.
- Payments:
  - The expense row is locked (`SELECT … FOR UPDATE`) before the balance is read, so concurrent payments cannot overpay.
  - `request_id` is the client's idempotency key: a resent request returns the original payment, and reusing the id for a different payment is a 409.
  - Corrections only void a payment (`voided_at`, `void_reason`), which the V1 trigger enforces. Voided payments are kept and listed, but never counted.
  - The form's "paid in full / part" choice is an optional `initialPayment`, saved in the same transaction as the expense.
- Calculation (`expenses.service.ExpenseCalculator`, the same rules as `lib/finance.ts`):
  - paid = `Σ` non-voided payments
  - outstanding = `max(0, amount − paid)`
  - status:
    - `PAID` when outstanding is 0
    - else `OVERDUE` when `due_date < today` (Colombo)
    - else `PARTIALLY_PAID` when paid > 0
    - else `UNPAID`

  The status filter uses the same rules in SQL. Nothing about the balance is stored.
- Edits: a full replace with optimistic locking (`version`), under the same row lock. The amount cannot go below what has already been paid (void a payment first). Moving an expense to another project or to company level writes an activity entry on the old project as well.
- `supplier_id` (implemented with the Suppliers module, 2026-10-24) is optional. A newly linked supplier must exist and be active; an expense that already names a supplier keeps it after the supplier is deactivated. `payee` stays required, and the expense dialog sends the supplier name as the payee.
- Not implemented, because nothing exists yet to back it:
  - The `attachment_*` columns stay null; there is no receipt-file upload yet.

  The category-specific fields (machinery, electricity) are accepted for any category, as in V1, which doesn't tie them to one.

## Suppliers and inventory

- **suppliers**: `name`, `contact_person`, `phone`, `email`, `address`, `supplies`, `credit_days`, and `active` (added by `V2__suppliers_active.sql`).
  - Implemented (2026-10-24):
    - Name and phone are required; everything else is optional. Text is trimmed, and blanks are stored as null. The email is checked only when given.
    - `credit_days` defaults to `company_profile.supplier_credit_days`, as the supplier dialog does.
    - Not unique on name or phone: shops share names, and branches share phones.
  - Suppliers are never deleted, because expenses (and later supplier invoices) reference them. They are deactivated (`active = false`) instead. An inactive supplier cannot be linked to a new expense, and existing links are untouched.
  - V2 added no index. Search is a "contains" match (`lower(name) LIKE '%…%'`), which a b-tree index can't serve, and a boolean flag on a small directory table isn't worth one. `ix_expenses_supplier` (V1) already covers the expense-to-supplier join.
- **materials**:
  - Columns: `sku` (unique), `name`, `category`, `unit_id`, `unit_cost`, `version`.
  - `unit_cost` is the **default unit cost**: a reference price entered in the catalogue and offered as the starting price on a receipt. Since FIFO (V4) it prices nothing, because every movement is costed from the cost layers. No movement changes it.
    - Under the weighted average (before V4) the ledger kept it at the current average, so materials from that time still hold their last average until someone edits it. That value has no effect on costing.
  - There is no reorder level and no low-stock tracking.
  - `active` (added by `V3__inventory_ledger_additions.sql`, default `TRUE`): materials are deactivated, never deleted, because the ledger references them. An inactive material takes no new receipts, issues or adjustments. Its history stays readable, and its issued stock can still be returned.
  - Implemented (2026-10-24):
    - SKU, name, category and unit are required. The SKU is unique ignoring case (409).
    - The unit must be active in Settings.
    - Once the material has any movement, the unit can no longer be edited, because the ledger's quantities are in that unit. The default unit cost can be edited at any time, and editing it revalues nothing.
- **supplier_invoices**:
  - Columns:
    - `supplier_id`, `invoice_no`, `invoice_date`, `due_date`
    - `allocation` (`STOCK` | `PROJECT`), `project_id`
    - `total_amount`, `notes`
    - `attachment_storage_key`, `attachment_filename`, `attachment_size`
    - `version`
  - Unique (`supplier_id`, `invoice_no`).
  - Checks:
    - `due_date ≥ invoice_date`.
    - `project_id` is set exactly when `allocation = 'PROJECT'`, and the project must be a construction project.
  - `due_date` defaults to `invoice_date + supplier.credit_days`.
  - `total_amount` equals the sum of the lines. The service checks this.
- **supplier_invoice_lines**:
  - Columns: `invoice_id`, `allocation` (copied from the invoice), `line_no`, `material_id`, `description`, `quantity > 0`, `unit_id`, `unit_price > 0`, `line_amount = round(quantity × unit_price, 2)`.
  - Unique (`invoice_id`, `line_no`).
  - On a `STOCK` invoice, every line must have a `material_id`.
- **supplier_payments**: `invoice_id` plus the common payment columns. A full payment is one row and partial payments are several rows. A payment entered on the invoice form is created in the same transaction.
- **stock_movements**: an append-only ledger.
  - Columns:
    - `material_id`, `movement_date`
    - `movement_type` (`RECEIVED` | `ISSUED` | `RETURNED` | `ADJUSTMENT`)
    - `quantity_change` (signed), `unit_cost`, `total_cost` (signed, set by the service)
    - `quantity_after`, `value_after` (the material's running balance after this movement)
    - `project_id`, `supplier_invoice_line_id`, `invoice_allocation`, `returned_from_movement_id`
    - `reason`, `reference`
  - Receipts from invoices:
    - Each invoice line has at most one receipt (unique `supplier_invoice_line_id`).
    - A composite foreign key on (`supplier_invoice_line_id`, `material_id`, `invoice_allocation = 'STOCK'`) ensures that only lines of `STOCK` invoices create receipts, and only for the line's own material.
  - Checks:
    - `RECEIVED` and `RETURNED` are positive. `ISSUED` is negative. `ADJUSTMENT` is non-zero and needs a `reason`.
    - `project_id` is set exactly when the type is `ISSUED` or `RETURNED`.
    - `returned_from_movement_id` is set exactly when the type is `RETURNED`.
    - `quantity_after ≥ 0` and `value_after ≥ 0`.
  - Returns:
    - A unique key on (`id`, `material_id`, `project_id`) lets a composite foreign key (`returned_from_movement_id`, `material_id`, `project_id`) force every return to point at an issue of the same material to the same project.
    - An insert trigger checks that the referenced row is an `ISSUED` movement and that the returned quantity does not exceed what remains un-returned. The trigger locks the issue row while it checks.
    - Materials that reached a project through a `PROJECT` supplier invoice or a manual `Materials` expense were never issued from stock, so they cannot be returned.
  - Ledger order:
    - Each material's ledger is ordered by `id`, which is the posting order. `movement_date` is the business date.
    - Costs are never recalculated retroactively. A late-entered (back-dated) receipt becomes the newest FIFO layer: it is used after every layer posted before it and affects only movements posted after it.
    - Index: (`material_id`, `id`), plus (`project_id`, `material_id`) for project usage.
  - Where receipts come from:
    - A posted `STOCK` invoice creates one `RECEIVED` movement for each line.
    - A `RECEIVED` movement without an invoice line comes from "Record stock received", for example a cash purchase or opening stock, and creates no payable.
  - Rows are never updated or deleted. Mistakes are corrected with an `ADJUSTMENT`, or a `RETURNED` movement for an issue.
  - Added by `V3__inventory_ledger_additions.sql`:
    - `supplier_id`: nullable FK to `suppliers`. `ck_stock_movements_supplier` allows it only on `RECEIVED` rows, so a manual receipt (cash purchase) can name its supplier. It is indexed (`ix_stock_movements_supplier`).
    - `request_id`: nullable UUID, unique (`uq_stock_movements_request`). It is the client's idempotency key for receipts, issues, returns and adjustments. NULL is allowed for movements the system posts, such as supplier invoice receipts later.
  - Added by `V4__inventory_fifo_cost_layers.sql`:
    - `costing_method` (`WAC` | `FIFO`, NOT NULL). Rows that existed before V4 are `WAC`, set through the column default when the column was added, so no row was updated. The default then became `FIFO` for every new row. A `WAC` row keeps the weighted-average cost it was posted at and has no allocations.
    - `uq_stock_movements_id_material` (`id`, `material_id`): the target of the composite keys that keep layers and allocations on the same material as their movement.
  - Implemented (2026-10-24, `inventory.service.StockMovementService` and `StockLedger`):
    - Each movement locks the `materials` row (`SELECT … FOR UPDATE`), checks the `request_id`, validates, prices the movement from the FIFO layers, and saves the movement, its layer or allocations, and the changed layer balances, all in one transaction. A posting is refused and rolled back if the open layers afterwards don't add up exactly to the ledger's `quantity_after` and `value_after`.
    - A resent `request_id` returns the first movement; the same id with different details is a 409.
    - Issues go only to `CONSTRUCTION` projects in `PLANNING`, `IN_PROGRESS` or `ON_HOLD`, for an active material, and never more than the stock on hand.
    - Returns reference an `ISSUED` row. The material and project come from it. Returns are allowed for an inactive material and for any project status, because stock already on site can always come back. The service checks the remaining quantity under the material lock; the V1 trigger checks it again.
    - Receipts need an active material, a unit cost above 0 (the UI rule), and, when a supplier is named, an existing active supplier.
    - Adjustments need an active material, a non-zero signed quantity and a reason of at least 5 characters. They never touch a project.
      - A reduction is costed FIFO and must not state a unit cost.
      - An increase must state its unit cost (`unitCost ≥ 0`), which becomes the new layer's cost. The cost is never guessed, because there is no purchase behind the stock.
    - Only issues and returns write an activity entry (`EXPENSE`, on the project), because they change project cost.
- **stock_cost_layers** (V4): one FIFO cost layer per batch of stock that came in.
  - Columns:
    - `material_id`, `source_movement_id` (unique), `origin` (`RECEIPT` | `ADJUSTMENT` | `LEGACY_BALANCE` | `LEGACY_RETURN`), `layer_date`
    - `original_quantity`, `unit_cost`, `original_cost`
    - `remaining_quantity`, `remaining_value`
    - `version`, plus the audit columns
  - Origins:
    - A receipt (opening stock included) creates a `RECEIPT` layer. A positive adjustment creates an `ADJUSTMENT` layer.
    - `LEGACY_BALANCE` is a material's stock and value when V4 ran.
    - `LEGACY_RETURN` is a return against a pre-FIFO issue.
  - The layer copies its movement: `original_quantity = quantity_change`, `original_cost = total_cost`, `unit_cost` = the movement's unit cost.
  - FIFO order is `id` order (posting order). It is deterministic even when two receipts share a date. `layer_date` is the business date, kept for display.
  - Only `remaining_quantity` and `remaining_value` ever change. Draws lower them, and returns put back what the issue took.
  - Checks:
    - `0 ≤ remaining_quantity ≤ original_quantity`, and `0 ≤ remaining_value ≤ original_cost`.
    - An empty layer is worth 0 (`remaining_quantity > 0 OR remaining_value = 0`).
    - A composite FK (`source_movement_id`, `material_id`) keeps the layer on its movement's material.
  - Index: partial (`material_id`, `id`) `WHERE remaining_quantity > 0`, for the open layers.
- **stock_cost_allocations** (V4): append-only. Each row is one movement's share of one layer.
  - Columns: `movement_id`, `material_id`, `layer_id`, `quantity`, `cost`, `reverses_allocation_id`.
  - A **draw** (from an issue or a negative adjustment) is negative and reverses nothing.
  - A **reversal** (from a return) is positive and names the draw it reverses (`ck_stock_cost_allocations_sign`). One issue can draw from many layers, and one layer can supply many issues.
  - Composite FKs keep the movement and the layer on the same material.
  - `trg_stock_cost_allocations_immutable` refuses updates and deletes.
  - `trg_stock_cost_allocations_reversal` locks the draw it reverses and checks two things: the reversal is on the same layer, and the reversals together don't exceed the draw's quantity or cost.
  - Invariant (checked by tests): a FIFO `ISSUED`, `RETURNED` or negative `ADJUSTMENT` movement's allocations sum exactly to its `quantity_change` and `total_cost`.

## Payroll

- **employees**: `name`, `role`, `phone`, `address`, `daily_wage > 0`, `overtime_rate > 0`, `status` (`ACTIVE` | `INACTIVE`), `joined_on`.
- **attendance**:
  - Columns: `employee_id`, `work_date`, `status` (`PRESENT` | `HALF_DAY` | `ABSENT`), `project_id`, `project_type` (must be `CONSTRUCTION`, composite FK), `notes`.
  - Unique (`employee_id`, `work_date`).
- **overtime_entries**:
  - Columns: `employee_id`, `work_date`, `project_id`, `hours` (`> 0 AND ≤ 8`), `hourly_rate > 0`, `approved`, `recorded_by`, `notes`.
  - `hourly_rate` defaults to the employee's `overtime_rate`, and the person entering it may change it.
- **salary_advances**: `employee_id` plus the common payment columns.
- **payroll_adjustments**:
  - Columns: `employee_id`, `week_start`, `advance_deduction`, `other_deduction`, `other_note`.
  - Unique (`employee_id`, `week_start`).
  - These are the owner's overrides for one week.
- **payroll_lines**: a frozen snapshot of one employee's week. It is written when the first payment for that employee and week is recorded, and it is never updated afterwards.
  - Columns:
    - `employee_id`, `week_start`, `week_end`
    - `present_days`, `half_days`, `payable_days`, `daily_wage`, `base_pay`
    - `overtime_hours`, `overtime_pay`, `gross_pay`
    - `advance_deduction`, `other_deduction`, `other_note`, `net_pay`
  - Unique (`employee_id`, `week_start`).
  - Checks: `gross_pay = base_pay + overtime_pay`, `net_pay = gross_pay − advance_deduction − other_deduction`, and `net_pay ≥ 0`.
- **payroll_line_costs**: `payroll_line_id`, `project_id` (nullable), `amount`. This splits `gross_pay` across projects for profitability.
- **advance_recoveries**: `advance_id`, `payroll_line_id`, `employee_id`, `amount > 0`.
  - It records which advances a week's deduction recovered, oldest first.
  - Composite foreign keys ensure the advance and the payroll line belong to the same employee.
  - Unique (`advance_id`, `payroll_line_id`).
- **payroll_corrections**: an explicit change to a frozen week.
  - Columns: `payroll_line_id`, `correction_date`, `wage_delta` (≠ 0), `project_id` (nullable), `reason` (not null).
  - It changes only the wages owed. It never changes `advance_deduction` or `advance_recoveries`, so advances cannot be counted twice.
  - Corrections stay separate records. Frozen payroll lines and their payment history are never rewritten.
  - Editing a correction is not supported yet. Before it is built, a migration must add an audit trail that records the previous value, the new value, the reason, who made the change and when.
- **payroll_payments**: `payroll_line_id` plus the common payment columns.
  - Payment is allowed from the week's payday (Settings > Wages: Saturday by default), when the UI pays wages; the original wording said "once the week has ended", which would forbid paying on payday itself. The UI offers per-worker payments and "Pay remaining".
  - The total paid can never exceed `net_pay + Σ wage_delta`.

**Freezing a paid week** (confirmed by the owner)
- The freeze applies to one employee for one week. It happens when the first payment for that employee and week is recorded, which is when the `payroll_lines` row is written.
- Other employees in the same week, and the same employee in other weeks, can still be edited.
- After the freeze, the following can no longer be inserted, changed or deleted:
  - that employee's `attendance` and `overtime_entries` for the week (Monday to Sunday)
  - that employee's `payroll_adjustments` for the week
  - the line and its cost and recovery rows
- Database triggers enforce the freeze, and the service reports the error to the user.
- Any later correction is entered as a `payroll_corrections` row, with a positive or negative amount, a reason and an optional project.
- If a negative correction leaves the worker overpaid, the overpayment is recovered as an `other_deduction` in a later week that has not been frozen. That week's `other_note` refers to the correction.

**Implemented (2026-10-24, `employees` and `payroll`; no migration was needed: V1 already has every table, constraint and trigger)**
- Employees:
  - Name, role, daily wage (> 0), overtime rate (> 0) and joining date are required, as in the dialog; phone and address are optional and trimmed.
  - There is no staff number and no duplicate check, because two workers may share a name.
  - Workers are never deleted; they are set `INACTIVE`. Inactive workers take no new attendance, overtime or advances, but their unpaid weeks can still be paid.
- Attendance (`PUT /api/v1/attendance/{date}`): the whole register for a day.
  - No Sundays, no future dates, only active workers who had joined by that date.
  - A project must be construction and In Progress or On Hold (the page's list).
  - Only rows that change are written, so a paid week can be re-saved unchanged. A worker left off the register loses that day's mark.
- Overtime: 0 < hours ≤ 8. The rate defaults to the worker's overtime rate. A project must be construction and not completed or cancelled. Entries start unapproved, and only approved hours are paid.
- The week: Monday to Sunday. Its `week_end` (stored on the line) is the payday from `wage_settings` (Saturday by default, Friday if set). It can be paid from payday onwards.
- Calculation (`payroll.service.PayrollCalculator`, the formulas under "Weekly payroll"):
  - `base_pay = round(payable_days × daily_wage, 2)`, and each approved overtime entry is `round(hours × rate, 2)`.
  - The project split prices each project's half-days on their own, and the rounding residue goes to the largest share, so `payroll_line_costs` always add up to gross. Overtime goes to its own project. Days without a project are the company share (`project_id` NULL).
  - The default advance deduction is everything outstanding on advances given up to payday, capped at gross. The owner's override is capped at outstanding and at gross.
  - "Outstanding" counts only recoveries already recorded by frozen weeks. Two unpaid weeks may both show the same deduction until one is paid; the freeze then records the real recovery.
  - A negative net (other deduction too large) is shown and blocks payment. It is never silently capped.
- Freeze and payment (`POST …/weeks/{weekStart}/employees/{employeeId}/payments`):
  - The worker's `employees` row is locked first. The first payment writes `payroll_lines`, `payroll_line_costs` and `advance_recoveries` (oldest advance first) in the same transaction.
  - Every payment is capped at `net_pay + Σ wage_delta − paid`. A refused payment rolls the freeze back too.
  - `request_id` makes resends safe: the same id returns the first payment (200), and the same id with different details is a 409.
  - Voiding a payment keeps the week frozen.
- A week whose advance deduction takes all its pay (net 0, gross > 0) can't be paid, so it is closed (`…/close`) to freeze it and keep the recovery. Without that, the advance would be deducted again.
- Corrections: only on frozen weeks.
  - The amount is ≠ 0. A project, if given, must be construction.
  - A week can't end up owing less than zero, and a negative correction can't take a project's (or the company's) labour for that week below zero.
  - Overpayment shows as `overpaid`. It is recovered manually as an other deduction in a later open week, as above.
- Advances: idempotent on `request_id`, active workers only. An advance can be voided only while nothing has recovered it.
- Project labour (`GET /api/v1/payroll/projects/{id}/labour`): paid weeks' `payroll_line_costs` for the project, plus corrections booked to it, plus open weeks priced live from attendance and approved overtime. Each worker-week is counted once, frozen or live.

## Database enforcement and service rules

**Enforced by the database** (constraints and triggers in `V1`)
- Payment and advance rows cannot be deleted. After insert, only the void columns can change, and a void is final.
- `stock_movements`, `payroll_lines`, `payroll_line_costs` and `advance_recoveries` cannot be updated or deleted.
- Returns must reference an `ISSUED` movement of the same material and project, and cannot exceed the quantity still un-returned on it.
- A paid employee-week is frozen.
- Composite foreign keys restrict features to project types (commission, delay terms, attendance, project invoices), exclude system-generated categories from expenses, and keep related rows on the same project or employee.
- The `request_id` and duplicate-record unique constraints listed above.
- Every CHECK that combines several conditions treats NULL as a failure.

**Enforced by the service**, inside a transaction that locks the parent row
- Overtime entries and stock issues are accepted only for construction projects. The owner decided this is a service rule, matching the project lists the UI already offers.
- Payment totals cannot exceed the remaining balance.
- FIFO costing, the layer balances and the running balances are calculated by the service.
- Schedule totals must match the contract value plus variations.
- Payments and write-offs are accepted only on billed installments.
- Invoice totals must equal the sum of their lines.
- Commission policy warnings are reported, and the owner can override them.
- Payroll calculations follow the formulas below.

## Calculations

These follow `lib/finance.ts` unless noted.

**Installments and receivables** (implemented in `revenue.service.ReceivableCalculator`, 2026-10-24)
- Deduction = the applied delay deduction, if `delay_deduction_terms.applied_installment_id` is this installment; otherwise 0.
- Net amount = `amount − deduction`.
- Received = `Σ client_payments.amount` where `voided_at IS NULL`. Written off = `Σ receivable_write_offs.amount`.
- **Outstanding = `max(0, net − received − written off)`** for billed installments, and 0 for unbilled ones. Only billed installments are receivables.
- Money is `NUMERIC(15,2)` and `BigDecimal` rounded `HALF_UP` to 2 decimals. Request amounts with more than 2 decimals are rejected, not rounded.
- Status, worked out on every read and never stored. "Today" is the Asia/Colombo date from the injected `Clock`.
  - `UNBILLED`: `billed_on` is null.
  - `PAID`: billed and outstanding is 0, whether settled by receipts, write-offs or both.
  - `OVERDUE`: billed, outstanding > 0 and `due_date < today`. This takes precedence over partly paid, as in the UI.
  - `PARTIALLY_PAID`: billed, outstanding > 0, not overdue, and something is settled (received + written off > 0).
  - `BILLED`: billed, outstanding > 0, not overdue, nothing settled.
  - `daysOverdue` = `today − due_date` for `OVERDUE`, otherwise 0.
- Mapping to the frontend's `ReceivableStatus` labels:

  | API | Frontend |
  | --- | --- |
  | `UNBILLED` | Upcoming |
  | `BILLED` | Due |
  | `PARTIALLY_PAID` | Partially Paid |
  | `OVERDUE` | Overdue |
  | `PAID` | Paid, or Written Off when `writtenOff > 0` |

  The UI counts only payments toward "Partially Paid"; the API also counts write-offs.

**Revenue and received are separate figures**
- Revenue recognised = `Σ net of billed installments` (dated `billed_on`). Billing is an explicit action and the only thing that recognises project revenue. Other income (implemented 2026-10-26) is recognised on its `income_date`, reported separately as the Other Income category; its receipts settle it and never add income.
- Received = `Σ` non-voided client payments. A payment never creates revenue, and a write-off is never money received.
- "Scheduled, not billed" (`unbilled`) = the amount of unbilled installments. It is expected revenue, not revenue.
- Company-wide summary (`/api/v1/receivables/summary`): outstanding and overdue over billed installments. "Partially paid" is the outstanding on billed installments with some settlement, overdue ones included, as the Receivables KPI counts it.

**Delay deduction** (implemented in `revenue.service.DelayDeductionCalculator`, matching `calcDelay()` in `lib/finance.ts`)
- `days_late = max(0, completion − contract_deadline)`
- `chargeable = max(0, days_late − grace_days)`
- The amount by rule:
  - `PER_DAY`: `chargeable × rate_per_day`
  - `PERCENT_PER_WEEK`: `floor(chargeable / 7) × percent_per_week ÷ 100 × contract_value`, rounded `HALF_UP` to 2 decimals
  - `FIXED_AMOUNT`: `fixed_amount` if `chargeable > 0`, else 0
- The result is capped at `max_deduction` when one is set. That gives the final amount.
- Completion date: the one given with the request, or else `projects.actual_completion`. It is never guessed: with neither, the request is rejected. It is stored in `delay_deduction_terms.actual_completion`, and the project's own dates are never changed.
- Applying requires:
  - enabled terms;
  - no deduction already applied (one per project, since there is one terms row per project);
  - the current `version`;
  - a billed target installment of the same project;
  - `chargeable > 0`.
- Amount: the final amount by default. The owner may agree a **smaller** figure, but never a larger one: the stored rule and cap are the ceiling. It also cannot exceed what is still payable on the installment before deduction (`amount − received − written off`).
- Reversing clears all four applied columns, including `actual_completion`, as `ck_delay_deduction_terms_applied` requires. The terms stay.
- Open question: the design said the owner "may apply a different final amount" without saying whether a higher one is allowed. The implementation allows only lower; revisit if the owner wants otherwise.

**Stock costing (FIFO, since V4 — replaces the weighted average)**

The oldest stock is used first. Each movement is posted with the `materials` row locked, and the open layers are also locked (`FOR UPDATE`). This is implemented in `inventory.service.FifoCosting`, which holds the arithmetic, and `StockLedger`, which does the posting. Money is rounded `HALF_UP` to 2 decimals, and unit costs to 4 decimals.

**The pricing rule, `share(q, pool)`.** Taking `q` out of a pool (a layer, or what is still out on one draw) that holds quantity `P`, is worth `W` and has unit cost `u` costs:
- `round(q × u, 2)`, capped at `W`;
- or exactly `W` when `q = P`.

The last of a pool therefore always takes exactly what is left. An emptied layer is worth 0.00, and no draw can take more than the layer is worth.

| Movement | Effect on layers | `total_cost` | `unit_cost` stored on the movement |
| --- | --- | --- | --- |
| `RECEIVED` | a new `RECEIPT` layer | `round(q × price, 2)` | the price |
| `ADJUSTMENT` + | a new `ADJUSTMENT` layer at the stated unit cost | `round(q × unit cost, 2)` | the stated cost |
| `ISSUED`, `ADJUSTMENT` − | draws from the open layers in `id` order, oldest first, until `q` is covered; one allocation per layer, each priced with `share` | `−Σ` draws | `|total| / q`, 4 dp, for display only |
| `RETURNED` (FIFO issue) | reverses the issue's own draws, **newest draw first**, and puts each quantity and cost back into the layer it came from; each priced with `share` over what is still out on that draw | `Σ` reversals | `total / q`, 4 dp, for display only |
| `RETURNED` (pre-FIFO `WAC` issue) | a new `LEGACY_RETURN` layer at the issue's own `unit_cost` | `share(q, still out on the issue)`: the last return takes the issue's remaining cost | the issue's `unit_cost` |

- The owner's example: receipt A of 10 at 2,000, receipt B of 10 at 2,400, then an issue of 12.
  - The issue draws 10 from A (20,000) and 2 from B (4,800), so the project is charged **24,800**.
  - What remains is 8 of B, worth **19,200**.
  - Nothing is averaged. A later, more expensive receipt never changes the 24,800.
- A return restores the composition of the original issue. Say the issue above is returned 1, then 2, then 9:
  - the 1 goes back to B at 2,400;
  - the 2 go back as 1 to B (2,400) and 1 to A (2,000), so 4,400;
  - the 9 go back to A, 18,000.
  - In total 24,800 comes back, exactly the issue cost, and A and B again hold exactly 10 / 20,000 and 10 / 24,000.
- Rounding:
  - Each draw or reversal is rounded once, to 2 decimals.
  - Intermediate products are not rounded.
  - The last of each layer, and the last of each draw, takes the exact remainder. A fully returned issue therefore nets to exactly 0.00 on the project. For example, 3 units worth 100.00 come back as 33.33 + 33.33 + 33.34.
- After every movement:
  - `quantity_after = Q + quantity_change`
  - `value_after = V + total_cost`, where `Q` and `V` are the previous row's values
  - the service then checks that `Σ remaining_quantity` and `Σ remaining_value` over the material's layers equal `quantity_after` and `value_after` exactly, and otherwise rolls the posting back
- The service rejects:
  - issues or negative adjustments larger than the stock on hand;
  - returns larger than the quantity still un-returned on the referenced issue.

  The V1 return trigger and the V4 reversal trigger check these again in the database.
- Project material usage (quantity and cost) = `−Σ` of the project's `ISSUED` and `RETURNED` movements. These are FIFO costs fixed when posted, or for pre-FIFO rows the average they were posted at.
- Stock on hand = the latest `quantity_after`.
- Stock value (per material and in `/valuation`) = `Σ remaining_value` of the open layers. This equals the latest `value_after`, `Σ total_cost` and the plain sums, and a reconciliation check plus tests confirm it.
- No average enters FIFO pricing. The display-only `unit_cost` on a multi-layer movement is never used to price anything.

**FIFO migration of existing data (V4)**
- A database used under the weighted average cannot be turned into honest FIFO layers. The posted issues were charged at the average, so replaying the history FIFO would charge projects different amounts than they were actually charged, and the resulting layers would no longer add up to the stock value the ledger records.
- V4 therefore rewrites nothing. For each material with stock on hand, it carries the current balance forward as **one `LEGACY_BALANCE` layer**:
  - its quantity and value are exactly the last row's `quantity_after` and `value_after`, at the unit cost `round(V / Q, 4)`;
  - its source is that last movement;
  - it is the oldest layer, so it is used first, and new receipts queue behind it.
- Materials at zero stock get no layer.
- Every pre-V4 movement keeps its cost and is marked `costing_method = 'WAC'`.
- Before carrying anything forward, V4 checks every material's ledger: the running balances must equal `Σ quantity_change` and `Σ total_cost`, and zero stock must be worth zero. If any material fails, the migration **stops** with an error naming the materials, and nothing is applied. No ledger is guessed or "fixed".

**Project costs**: each cost has exactly one source.

| Cost | Source |
| --- | --- |
| Materials | `PROJECT` supplier invoices + `ISSUED` minus `RETURNED` movements + manual `Materials` expenses |
| Labour | attendance (`daily_wage` per present day, half for a half day) and approved overtime (`hours × hourly_rate`) on the project. Frozen weeks use `payroll_line_costs` plus `payroll_corrections`. |
| Commission | confirmed (not voided) arrangements: the stored `commission_amount` (= contract value × rate), recognised at confirmation. Payments settle it and are not a cost. |
| Other | manual project expenses in every other category, including machinery rental |

**Profitability**
- Profit = revenue − write-offs − project costs.
- Margin = profit ÷ revenue.
- It is shown as *Estimated* until the project is `COMPLETED`, then as *Recorded*.

**Payables**
- Supplier invoice outstanding = `total − Σ payments`.
- Expense outstanding = `amount − Σ payments`.
- Commission outstanding = `commission_amount − Σ active payments`, for confirmed arrangements only (drafts and voids owe nothing).
- An invoice or expense is overdue when something is still outstanding and `due_date < today`.

**Weekly payroll**
- `payable_days = present + 0.5 × half_days`
- `base_pay = payable_days × daily_wage`
- `overtime_pay = Σ approved hours × hourly_rate`
- `gross = base_pay + overtime_pay`
- Advance deduction = the adjustment override, or else all outstanding advances given up to payday, but never more than gross.
- `net = gross − advance deduction − other deduction`
- Remaining = `net + Σ wage_delta − Σ payroll payments`. Corrections only exist on frozen weeks.

## Preventing double counting

- **Purchasing stock is not a project cost.** A `STOCK` invoice creates a payable and `RECEIVED` movements. Cost reaches a project only through `ISSUED` movements, and `RETURNED` movements reverse it. A `PROJECT` invoice is a project cost directly and creates no stock movements.
- **Each manual purchase has one record.** Credit purchases from suppliers are entered as supplier invoices. A manual `Materials` expense is for cash purchases that are not entered as invoices. The service warns when an expense's supplier and invoice number match an existing supplier invoice.
- **Supplier payments change only the payable,** never cost.
- **Labour is counted once.** The labour cost is gross wages, taken from attendance and overtime. A salary advance is cash paid ahead of payday that `advance_recoveries` later recovers. It is not an expense and not a second payment. The worker's total received is the sum of advances and payroll payments, which equals net pay plus the recovered advances. Corrections to a frozen week change only wages, never advance recoveries.
- **Commission and labour costs come only from their own modules.** Their categories are system-generated and cannot be used for a manual expense.
- **Revenue is recognised once, at billing.** Payments settle it. Write-offs and delay deductions are separate reductions. Variations are separate installments, and the contract value never changes.
- **Payments cannot be recorded twice.** Each one is tied to a single obligation, has a unique `request_id` and is capped at the remaining balance.

## Examples

**FIFO stock, issue and return**
1. A `STOCK` invoice for 100 bags of cement at 2,400.
   - Payable: 240,000. Stock: layer A, 100 bags, 240,000. Project cost: 0.
2. A second `STOCK` invoice for 50 bags at 2,550.
   - Payable: +127,500. Stock: A (100 at 2,400) + B (50 at 2,550) = 150 bags, 367,500.
3. Issue 110 bags to SK-2026-014.
   - The issue draws all 100 of A (240,000) and 10 of B (25,500).
   - Project cost: 265,500. Stock: 40 bags of B, 102,000.
4. Return 15 bags against that issue.
   - Newest draw first: 10 go back to B (25,500) and 5 to A (12,000).
   - Project cost: 228,000. Stock: A 5 + B 50 = 55 bags, 139,500.
5. Pay both invoices, in one or several payments each.
   - Payables: 0. Project cost: still 228,000.

The purchases never appear as project cost.

**Billing, payments and delay deduction**
- The final installment is 2,000,000 and is billed, so revenue is 2,000,000.
- Delivery is 13 days late with 3 grace days: 10 chargeable days × 15,000 = a 150,000 deduction, applied to that installment.
- Net amount and revenue: 1,850,000.
- Payments of 1,000,000 and 500,000 leave 350,000 remaining. It is overdue once the due date passes.
- The contract value does not change.

**Design commission**
- Contract value: 1,500,000. Recipients: 12% and 8% = 20%, so 180,000 and 120,000, whatever has been collected so far.
- Adding 2% more would trigger the pool warning. The owner may still confirm it as an exception.

**Payroll with an advance**
- 5 full days + 1 half day at 3,500 = 19,250. Approved overtime of 4 h × 656.25 = 2,625. Gross: 21,875.
- A 5,000 advance is deducted, so net = 16,875.
- Labour cost: 21,875. Paid to the worker: 5,000 + 16,875 = 21,875.

The advance is not counted a second time.

**Correction to a paid week**
- After the week above is paid, a missed half day is found.
- A `payroll_corrections` row of +1,750 (with a reason and the project) is added.
- Labour cost: 23,625. Remaining owed: 1,750.
- The frozen line, the attendance rows and the 5,000 advance recovery do not change.

## Frontend alignment

The schema was compared with the frontend types, forms and calculations.

**Areas where the schema and the frontend match**
- Clients, projects (agreement metadata included), installments and billing, variations, client payments, write-offs, delay deduction terms (apply and reverse), other income and receipts.
- Commissions (draft or confirmed, with warning-only policy checks), manual expenses with their category-specific fields and payments, suppliers, supplier invoices and payments.
- Stock received, issued and adjusted; employees, attendance, overtime approval, advances, payroll adjustments and payments; settings lists; the activity feed; all six reports.

**Differences from the v1 draft, changed to follow the UI**
- Retention money has been removed. The UI explicitly separates delay deductions from retention and has no retention feature.
- The machinery rental tables have been removed. In the UI, a rental is an expense.
- Removed because the UI does not use them: service lines on invoices, invoice lines split between destinations, a separate table of commission recipients, effective-dated wage rates, finalized payroll periods, a project link on other income, and reference codes for clients, suppliers and employees.
- A policy breach on commission is now a warning that the owner can override, instead of a rejection.
- Payment methods are now a lookup table that matches the editable Settings list.

**Owner decisions (2026-10-24)**
1. **Material returns:** each return is linked to the originating project and its stock issue. The stock goes back to company stock, and the project's material cost falls by the original issue cost of the returned quantity.
2. **Low stock:** removed. There is no reorder level, no low-stock status and no alerts.
3. **Stock costing:** FIFO, with persistent cost layers and issue allocations (see [Stock costing](#calculations)). This was changed by the owner on 2026-10-24, from the weighted average originally chosen. Movements posted under the average keep their costs (`costing_method = 'WAC'`).
4. **Paid payroll weeks:** a week is frozen for an employee at that employee's first payment for it. Later changes are made through `payroll_corrections`.
5. **Revenue categories:** fixed to the four categories and shown read-only in Settings.
